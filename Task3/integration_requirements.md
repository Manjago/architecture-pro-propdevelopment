# Требования к безопасной интеграции ("Умный дом")

## 1. Контекст интеграции
Внедрение сервисов "Умный домофон" и "Умный шлагбаум" предполагает взаимодействие между мобильным приложением собственника (PropDevelopment App) и облачной платформой партнера (Smart Home Cloud).

**Цель:** Обеспечить безопасное управление физическим доступом (открытие дверей) без раскрытия ПДн собственников партнеру.

## 2. Протоколы и стандарты

| Компонент взаимодействия | Протокол | Аутентификация | Шифрование |
| :--- | :--- | :--- | :--- |
| **Mobile App -> API Gateway** | HTTPS (REST) | JWT (OIDC) | TLS 1.3 |
| **API Gateway -> Tenant Core** | gRPC | mTLS (Istio) | mTLS |
| **Tenant Core -> IoT Adapter** | gRPC | mTLS | mTLS |
| **IoT Adapter -> Partner Cloud** | HTTPS (REST) | **mTLS + API Key** | TLS 1.3 |

## 3. Требования к безопасности

### 3.1. Идентификация и Аутентификация (Identity & AuthN)
1.  **Mobile App:** Использует **Biometric Auth** (FaceID/TouchID) для подтверждения команды "Открыть дверь". Это фактор *Inherence* (неотъемлемая характеристика), что критично для физического доступа.
2.  **Service-to-Service:** Взаимодействие с облаком партнера должно происходить через **mTLS (Mutual TLS)**.
    *   PropDevelopment имеет клиентский сертификат, выданный партнером.
    *   Это защищает от атак Man-in-the-Middle и гарантирует, что запрос пришел именно от нас.

### 3.2. Авторизация (AuthZ)
1.  **Принцип минимальных привилегий:**
    *   Партнер не должен знать ФИО жильца. Ему передается только `user_uuid` или `apartment_id`.
    *   Мобильное приложение не ходит в API партнера напрямую. Все запросы проксируются через Backend (IoT Adapter).
2.  **RBAC:**
    *   Только пользователь с ролью `OWNER` и привязкой к конкретному `FLAT_ID` может отправить команду на открытие домофона этого подъезда.

### 3.3. Защита данных (Data Protection)
1.  **Data Minimization:** В API партнера не передаются ПДн.
2.  **Logging:** Факт открытия двери логируется в Audit Log PropDevelopment (кто, когда, какую дверь открыл), но не содержимое видеопотока.

### 3.4. Сетевая безопасность
1.  **Egress Filtering:** Доступ к API партнера разрешен только из подов `iot-adapter-service`.
2.  **Rate Limiting:** Настроить лимиты на API Gateway, чтобы злоумышленник не мог спамить командами открытия дверей (DoS атака на домофон).

## 4. Схема потока данных (Data Flow)

1.  **Пользователь** нажимает "Открыть шлагбаум" в приложении.
2.  Приложение запрашивает **FaceID**.
3.  Запрос `POST /api/v1/barrier/open` летит на **API Gateway**.
4.  Gateway проверяет валидность **JWT токена**.
5.  Gateway пересылает запрос в **Tenant Core**.
6.  Tenant Core проверяет в БД: "Имеет ли этот юзер право открывать шлагбаум ЖК 'Солнечный'?" (**Authorization**).
7.  Если OK -> запрос летит в **IoT Adapter**.
8.  IoT Adapter подписывает запрос **mTLS сертификатом** и отправляет в **Partner Cloud**.
9.  Partner Cloud дает команду на устройство.
10. Шлагбаум открывается.
