# Проверочный лист для аудита информационной безопасности
## Компания: PropDevelopment

---

## Обоснование выбора разделов

При составлении проверочного листа для PropDevelopment учтены следующие ключевые факторы:

### Приоритетные области аудита

1. **Управление доступом** — *Критический приоритет*
   - В компании выявлены проблемы с разграничением доступа между партнёрами (управляющими компаниями)
   - Партнёр из одной УК может видеть или изменять данные клиентов другой УК
   - Несколько точек регистрации клиентов без координации между ними
   - Единственный специалист по ИБ не получает информацию обо всех изменениях в системах

2. **Безопасность данных** — *Критический приоритет*
   - Компания обрабатывает персональные данные клиентов и собственников (ФИО, телефон, email, паспортные данные для сделок)
   - Интеграция с госорганами для онлайн-сделок требует соответствия ФЗ-152
   - Клиенты жалуются на отображение чужих данных в личном кабинете — признак утечки/смешения данных
   - Контракты API партнёров явно содержат категории персональных данных

3. **Защита инфраструктуры** — *Высокий приоритет*
   - Гибридная инфраструктура (собственный ЦОД + облачные ресурсы) требует комплексной защиты
   - Внешний доступ для клиентов и собственников через мобильные приложения и веб-витрину
   - Планируется интеграция с IoT-устройствами («Умный дом»: домофоны, шлагбаумы)

4. **Управление инцидентами** — *Высокий приоритет*
   - Недавняя утечка данных у конкурента вызвала обеспокоенность руководства
   - Необходимо оценить готовность к реагированию на инциденты

### Адаптация разделов

- **Раздел «Физическая безопасность серверных»** — сохранён частично, так как у компании есть собственный ЦОД
- **Добавлен акцент на безопасность API** — ключевой вектор угроз для PropDevelopment
- **Добавлен акцент на IoT/Умный дом** — планируемая интеграция с партнёром по домофонам и шлагбаумам
- **MDM** — применим для корпоративных устройств сотрудников, работающих с CRM и данными клиентов

### Исключённые/пониженные в приоритете области

- Детальный аудит рабочих станций конечных пользователей (фокус на серверной инфраструктуре и API)
- Безопасность разработки (SDLC) — отдельная тема, не входящая в текущий scope аудита

## Проверочный лист

### I. Управление доступом

| № | Вопрос | Да/Нет/Частично | Комментарий |
|---|--------|-----------------|-------------|
| 1 | Используется ли многофакторная аутентификация (MFA) для доступа к критическим системам и сервисам? | **Нет данных** | Требуется проверка. Рекомендация: внедрить MFA для всех сотрудников с доступом к ПДн клиентов (CRM, client-crm-app, tenant-core-app). Приоритет — администраторы и сотрудники УК. |
| 2 | Настроены ли требования к сложности паролей и их регулярное обновление? | **Частично** | Active Directory упоминается в архитектуре — вероятно, базовые политики настроены. Требуется аудит: соответствие требованиям (мин. 12 символов, спецсимволы, ротация 90 дней). |
| 3 | Проводится ли аудит и пересмотр учётных записей с повышенными привилегиями на регулярной основе? | **Нет** | Упомянуто, что специалист по ИБ не получает информацию о всех изменениях. Процесс ревизии привилегированных учётных записей отсутствует или не формализован. **Критический риск.** |
| 4 | Реализован ли принцип минимальных привилегий при назначении ролей и прав доступа? | **Нет** | Прямое указание в описании: партнёр из одной УК может видеть/изменять данные другой УК. Принцип least privilege не соблюдается. **Критический риск.** |
| 5 | Автоматически ли удаляются или деактивируются учётные записи после увольнения или изменения должности сотрудников? | **Нет данных** | Упомянуты изменения в составе руководителей IT-команд, нарушившие передачу информации. Требуется проверка процесса offboarding. |
| 6 | Ведётся ли журналирование всех операций доступа к системам и данным? Кто имеет доступ к журналам? | **Частично** | Вероятно, базовое логирование есть на уровне БД и приложений, но централизованный сбор и анализ (SIEM) не упоминается. Доступ к логам не регламентирован. |
| 7 | Используются ли механизмы контроля доступа на основе атрибутов (ABAC) для повышения гибкости управления доступом? | **Нет** | Судя по проблеме с партнёрами УК, используется простая ролевая модель без учёта контекста (какая УК, какой ЖК). Необходимо внедрение ABAC или расширение RBAC с учётом tenant isolation. |
| 8 | Используются ли системы аутентификации пользователей для доступа к системам? | **Да** | Active Directory присутствует в архитектуре для внутренних пользователей. Для внешних (клиенты, собственники) — аутентификация через мобильное приложение и веб-витрину. |
| 9 | Созданы ли замкнутые контуры для подсистем, работающих с чувствительными данными? | **Нет** | Описание указывает: «Со стороны систем обработки данных нет ограничений на доступ к данным». Data-домен имеет неограниченный доступ. **Критический риск для ПДн.** |
| 10 | Ограничен ли доступ к системам из внешних источников? | **Частично** | Межсетевой экран (firewall) используется для внешних пользователей. Однако API партнёров не имеют единых политик безопасности. Требуется аудит правил firewall и WAF. |
| 11 | Ведётся ли единый реестр учётных записей? | **Частично** | Active Directory для сотрудников. Для клиентов и собственников — отдельные системы (client-crm-app, CRM для собственников). Единого реестра нет. |
| 12 | Используются ли средства управления учётными записями на базе единого реестра (IAM/IDM)? | **Нет** | Централизованная система управления идентификацией не упоминается. Рекомендация: внедрить IAM (Keycloak, Azure AD B2C) для унификации. |
| 13 | Применяются ли средства для отзыва прав доступа? | **Нет данных** | Требуется проверка. Учитывая проблемы с передачей информации ИБ-специалисту, вероятно, процесс не автоматизирован. |
| 14 | Используются ли средства централизованного контроля доступа к API партнёров? | **Нет** | Прямое указание: «API управляющих компаний используются без единых политик по безопасности». **Критический риск.** Необходимо внедрить API Gateway с централизованной авторизацией. |

### II. Безопасность данных

| № | Вопрос | Да/Нет/Частично | Комментарий |
|---|--------|-----------------|-------------|
| 1 | Разработана ли политика классификации данных, и актуализируется ли она в соответствии с действующим законодательством? | **Нет** | Описание указывает на отсутствие системного контроля потоков данных. Классификация не проводилась. Требуется разработка политики с учётом ФЗ-152, категоризация: публичные, внутренние, конфиденциальные (ПДн), секретные (паспортные данные для сделок). |

Шифрование at-rest на уровне БД — требуется проверка. Для БД с ПДн (client-crm-db, crm-db, client-mart-estate-db) шифрование обязательно. |
| 3 | Реализованы ли механизмы управления ключами шифрования (KMS, HSM)? | **Нет данных** | Не упоминается. При наличии шифрования — требуется аудит хранения и ротации ключей. |
| 4 | Проводится ли регулярное резервное копирование данных? Хранятся ли резервные копии в защищённых хранилищах? | **Да** | Прямое указание: «Для всех баз данных выполняется резервное копирование данных на глубину, необходимую для восстановления». Место хранения и защита копий — требуется уточнение. |
| 5 | Выполняется ли регулярное тестирование процесса восстановления данных из резервных копий? | **Нет данных** | Требуется проверка. Рекомендация: проводить DR-тестирование не реже 1 раза в квартал. |
| 6 | Ограничен ли доступ к резервным копиям данных, и зашифрованы ли они? | **Нет данных** | Требуется аудит. Резервные копии содержат ПДн — шифрование обязательно по ФЗ-152. |
| 7 | Ведётся ли учёт персональных данных, и применяются ли специальные процедуры обработки и хранения для различных типов данных? | **Нет** | Проблема явно обозначена: несколько точек регистрации клиентов без координации, нет единого реестра ПДн. Требуется разработка реестра обработки ПДн (требование ФЗ-152). **Критический риск комплаенса.** |
| 8 | Осуществляется ли мониторинг доступа к данным на основе их классификации, и используются ли метки безопасности? | **Нет** | Классификация отсутствует (п.1), мониторинг не настроен. Data-домен имеет неограниченный доступ ко всем данным. |
| 9 | Разработаны ли процессы и системы Data Governance для управления данными? | **Нет** | Прямое указание: «Проблема управления и хранения потоков данных блокирует реализацию новых продуктов». Data Governance отсутствует. |
| 10 | Реализованы ли системы или процессы безопасного уничтожения данных? | **Нет данных** | Требуется проверка. Важно для соответствия ФЗ-152 (право на удаление ПДн). |
| 11 | Используются ли системы или процессы контроля целостности данных? | **Нет** | Проблема: клиенты видят в ЛК данные других клиентов. Это указывает на нарушение целостности или логики выборки данных. **Критический дефект.** |
| 12 | Реализованы ли системы или процессы контроля сохранности данных? | **Частично** | Резервное копирование есть. Контроль целостности (checksums, reconciliation) — не упоминается. |
| 13 | Применяются ли средства или процессы анонимизации/псевдонимизации данных? | **Нет** | Для Data-домена (BI, ML, AI) требуется анонимизация ПДн перед обработкой. Текущее состояние — данные передаются «как есть». |
| 14 | Разработана ли инструкция по процессу восстановления данных? | **Нет данных** | Требуется проверка наличия и актуальности DRP (Disaster Recovery Plan). |

| 10 | Реализовано ли автоматическое обновление сигнатур защиты от вредоносных программ? | **Нет данных** | Требуется проверка для серверов и контейнеров. |
| 11 | Осуществляется ли фильтрация трафика между сетевыми сегментами? | **Нет** | Описание указывает на отсутствие ограничений между доменами. Data-домен имеет доступ ко всем данным. Сегментация на уровне сети не реализована. |
| 12 | Используются ли средства для контроля периметра доступа (WAF, API Gateway)? | **Нет** | API партнёров используются «без единых политик по безопасности». WAF и API Gateway не внедрены или не настроены корректно. **Критический риск.** |

| 4 | Проводятся ли симуляции инцидентов (tabletop exercises, red team) для проверки готовности? | **Нет** | При одном специалисте по ИБ ресурсов на учения нет. Рекомендация: провести после усиления команды ИБ. |

| 6 | Как часто проводятся внутренние и внешние аудиты безопасности? | **Редко/Никогда** | Текущий аудит — первый комплексный. Рекомендация: ежегодный внешний аудит, ежеквартальный внутренний. |
